# `suggestion` 格式

## Item format

| Payload 字段      | 填写语义                                                          |
| ----------------- | ----------------------------------------------------------------- |
| `现状 / 依据`     | 当前 workflow、限制或改进机会的具体依据                           |
| `预期收益`        | 实施后的可观察收益，以及不实施时保持的现状                        |
| `原始建议 / 方案` | 来源中的建议或方案；补充的方案标为 `proposed`，缺失时写 `unknown` |

## Display body

```markdown
<用一句话说明建议适用于什么场景、当前做法有什么限制，以及改进后会产生什么实际收益；必要时注明来源和原始结论>

- 适用场景：<使用该 workflow 的具体任务、用户或前提>
- 当前限制：<现有做法带来的额外步骤、成本或体验限制>
- 改进后结果：<实施建议后可直接观察到的变化>
- 实际收益：<节省的工作、改善的体验或获得的能力>

### Proposal

<推荐改进、理由、最小有效范围和验证方式>

| 对比项                           | 改进前       | 改进后       | 变化 / 影响 |
| -------------------------------- | ------------ | ------------ | ----------- |
| <行为、体验或 architecture 维度> | <可观察结果> | <可观察结果> | <具体差异>  |

<明确不变：关键 happy path、兼容性或非目标的实际结果>

---

- 收益：<实施改进后的具体价值>
- 代价 / 风险：<实施成本、副作用和 tradeoff>
- Effort / 可逆性：<总成本、范围、假设和回退难度>
- 待验证：<尚未确认的现状、收益或副作用；没有则写“无”>
```

performance 对比写明 workload、baseline、预期值和差值。architecture 对比写明前后 flow、ownership 及修改影响。

## Actions

- 首次处理提供“Accept 后续统一处理 / Reject / 先验证 / 延后”。
- 仅在能隔离改动并安全回退时提供“试做当前项”。
- 进入终态时，在 `结论 / 决策` 中记录接受、拒绝或其他处理结论。
- 若后续证据表明核心性质改变，保持 `discussing` 并请用户确认新类型或忽略该项。

## Example

示例：交互查看结果时，工具只输出 JSON，用户需要手工排版后才能快速比较各行；增加可选 table 输出可直接生成易读结果，但现有 JSON 行为本身没有缺陷，因此为 `suggestion`。
