# `issue` 格式

## Item format

| Payload 字段      | 填写语义                                                       |
| ----------------- | -------------------------------------------------------------- |
| `触发条件 / 证据` | 能支持缺陷、回归或风险判断的具体前提、reproduction、测试或观测 |
| `影响 / 收益`     | 当前的可观察影响，以及修复或接受风险后的结果                   |
| `原始建议 / 选项` | 来源中的修复建议或处理选项；缺失时写 `unknown`                 |

## Display body

```markdown
<用一句话说明在什么条件下会触发问题、当前会出现什么结果，以及造成什么实际影响；必要时注明来源和原始结论>

- 触发：<具体输入、环境、状态或操作>
- 当前结果：<触发后实际出现的行为、输出或状态变化>
- 实际影响：<受影响的用户、workflow、数据或系统，以及影响范围>

### Proposal

<推荐修复或风险处理、理由、最小有效范围和验证方式>

| 对比项                           | 解决前       | 解决后       | 变化 / 影响 |
| -------------------------------- | ------------ | ------------ | ----------- |
| <行为、性能或 architecture 维度> | <可观察结果> | <可观察结果> | <具体差异>  |

<明确不变：关键 happy path、兼容性或非目标的实际结果>

---

- 收益：<解决问题后的具体价值>
- 代价 / 风险：<实施成本、副作用和 tradeoff>
- Effort / 可逆性：<总成本、范围、假设和回退难度>
- 待验证：<尚未确认的触发条件、当前结果或影响；没有则写“无”>
```

performance 对比写明 workload、baseline、预期值和差值。architecture 对比写明前后 flow、ownership 及修改影响。

## Actions

- 首次处理提供“Accept 后续统一处理 / Reject / 先验证 / 延后”。
- 仅在能隔离改动并安全回退时提供“试做当前项”。
- 进入终态时，在 `结论 / 决策` 中记录修复、接受风险或其他处理结论。
- 若证据不再支持缺陷或风险，保持 `discussing` 并请用户确认新类型或忽略该项。

## Example

示例：执行 `tool sync --dry-run` 时会触发目标文件写入，mtime 随之变化，导致依赖 mtime 判断增量更新的任务重新处理该文件，因此为 `issue`。
